# UI layer — per-file design notes

Per-file notes for `MainActivity.kt` and `ui/**`: the "why" behind each file, its gotchas, and test coverage. Read the relevant bullet before modifying a file here; update it when behavior changes. Cross-cutting rules live in `/CLAUDE.md` («Conventions & gotchas») and are assumed, not repeated.

## Cross-file wiring (MainActivity)

- **Overlay stack** — all overlays render after `Scaffold` in one `Box`, each gated by a `rememberSaveable` flag (`showScan`, `showSettings`, `showUpload`, `showAdmin`/`showProvisioning`/`showCheckChip`/`showCheckMemberChip`/`showJudgeScan`, `bindSlot`/`unbindSlot`, `teamFlowStep`/`confirmTeamId`). `showJudgeScan: String?` is `null | "start" | "finish"` (the admin menu's two rows set it, `JudgeScanScreen` reads it as `eventType`) rather than a `Boolean`, since the same host serves both fixed-mode pages. Sibling `BackHandler`s are registered in stacking order (later wins) and each fires only when no deeper overlay is up. Flags reset on `onScanClick` and on team switch (`LaunchedEffect(selectedTeamId)`) — `showUpload` mirrors `showSettings` and is **not** reset on team switch (only reachable via Settings). Theme/economy/admin-session are collected **once** here and threaded down as params (no second `collectAsState`). **`lastRealTeamId` guard** — the app is now portrait-locked (`android:screenOrientation="portrait"` on `MainActivity`, see Config/references), which eliminates orientation-triggered Activity recreation, but other config changes (multi-window resize, font-scale) still recreate it and transiently reset `selectedTeamId`'s `collectAsState()` to `null`. A `rememberSaveable var lastRealTeamId` tracks the last genuine non-null team id; the effect body (overlay resets + the recording-stop check) early-returns unless `selectedTeamId` is non-null **and** differs from `lastRealTeamId`, so a transient-null recreate blip no longer closes open overlays (e.g. the photo-capture camera) or drops a still-relevant team's recording.
- **Scan wiring** — the overlay is fed `scanBindings` (`nfcUid → numberInTeam`) **filtered to the current roster's slots** — a correctness guard: a stale binding for a removed member would otherwise let its chip falsely complete a take (`complete` only compares `present.size` to `expectedCount`). The FAB is gated on a resolved team (else routes to the picker); `onScanTag` refuses (`BadKp`) an empty roster. The opening tap and every later tap share one `ScanInput` path (`Captured` reuses the already-read `(code, uid)`, `Live` reads them) → `legendRepo.unlock` (if a code) → `classifyTag` → persist via `MarkRepository`. **`attachLocation` fires only on the new-take branch** (one-shot `currentLocationProvider.current()`, `null` = no-op). `ScanScreen.process()` plays `scanFeedback.play(feedbackFor(event))` after the `currentOnScanTag` result so every tap (incl. idempotent re-taps) fires exactly one of the three outcomes. **Check method:** the new-take branch passes `checkMethod = event.checkMethod` into `startKpTake`; `confirm = { target -> … }` is one attempt per call: it reads `scanTake.markId` then (stable for the whole loop — confirm mode drops every tap before `onScanTag`, so the take id can't change) and runs `markRepo.confirm(id, target, System.currentTimeMillis())` on `container.applicationScope.async { }.await()` (an unreachable null id → `Error`), so every retry/«Повторить» re-POSTs the same take and a request in flight when the overlay closes still lands (and writes `confirmedAt` if accepted).
- **Open-on-tap** — there is a **single open source**: the live-idle foreground path publishes `CapturedScan(code, uid, sample)` (no NDEF cold/warm launch — raw `K24` chips can't cold-launch the app). A `LaunchedEffect(captured, teamState)` dispatches it: another overlay up → drop; `Present` → open scan; `None`/`Missing` → open the picker; `Loading` → **return without clearing** so the next state transition re-fires. `ScanScreen` drains `pendingScan` so the opening tap is byte-identical to later taps. Auto-close on window expiry and on completion (a ~3.3 s green «Готово!» hold matching the completion fanfare — see the checkpoint-take celebration below).
- **Checkpoint-take celebration** — the tap that transitions a session from incomplete to complete (which can land on a **Kp** event, when members were buffered before the КП tap) plays the ordinary success scan feedback first, then `scanFeedback.checkpointCompleteFanfare()` after a short delay (for a `cloud`/`local` take the fanfare, hold and `onCompleted` wait for the server confirm — see `ScanScreen`); `ScanScreen`'s `SUCCESS_HOLD_MS` (3 300 ms, final tick + fanfare length) holds the green «Готово!» screen for that whole sequence before auto-closing, and only that auto-close path fires `onCompleted` (never expiry or manual close). `MainActivity` sets a one-shot `pendingCelebration` (plain `remember`, not `rememberSaveable` — a recreate mid-celebration deliberately drops it; also cleared on team switch) and navigates to «Отметки» (`switchToTab(0)`). `MarksScreen` consumes `celebration` on arrival: scrolls its `LazyColumn` to the bottom, then plays `onCoinSound()` together with a bouncy scale/fade pop-in on the new last tile, and calls `onCelebrationDone()`.
- **Local-mode switch + PTR re-route** — the Settings «Данные» switch position is **derived, not stored**: `isPinned(container.raceLease.collectAsState(), selectedRaceId ?: nearestRaceId, trustedClock.trusted() ?: wallClock)`, so a handback or expiry flips it live even while Settings is open. `onLocalModeChange` launches `syncCoordinator.enterLocalMode()`/`exitLocalMode()` on `applicationScope` and maps the returned `LocalModeOutcome` to a RU Toast. «Команда»'s pull-to-refresh now calls `syncCoordinator::refreshAll` (intentionally broadens the pull from teams-only to races+teams+legend+member-tags); «Легенда»'s pull passes `source = syncCoordinator.sourceFor(raceId)` (else a pinned pull would silently `Skipped` against the cloud guard); the races picker's pull stays Cloud-only (races isn't race-scoped); `onRaceSelected`'s prefetch routes teams+legend through `sourceFor(raceId)`.
- **Map tab wiring** — **4 pager pages**: Отметки (0) / Легенда (1) / **Карта (2)** / Команда (3); `switchToTab(3)` and the readiness checklist's `ReadinessAction.BindChips` target Команда (and `ReadinessAction.OpenMap` targets Карта at index 2) at index 3 (was 2) — any new hard-coded page index must follow this order. `mapRepo = container.mapRepository` (read alongside the other repos; the `by lazy` singleton is built on first composition — no disk I/O on the main thread, the repo seeds `downloaded` off-main); `state`/`downloaded` collected here. `downloaded` is `null` until that seed lands → `mapAvailabilityNow` and `mapBase` stay `null` (plain background, no `Online → Offline` style flip on a cold start). `mapAvailability(...)` is computed from the selected race's `mapUrl` (from `races`), the downloaded set and the download state. **`settledPage` gate:** `mapActive = pagerState.settledPage == PAGE_MAP` — the native `MapView` (and its location-component GPS client) exists only on the settled Карта page, never off-screen or while a `0↔3` tab animation sweeps through page 2; `mapPins` is rebuilt only while `mapActive`; the host passes `trackLinesNow` as-is — `TrackMapView` (composed only while active) builds its GeoJSON off the main thread. **Track filter wiring:** `showAllTrackPoints` is collected once at Activity level from `container.trackFilterPreference.showAllPoints` (next to `trackProfile`) and passed with its setter into `Kolco24AppRoot`; `safeTrack` is `remember(track, selectedTeamId)` (an unchanged track keeps its instance, so keys compare by identity). The sort + filter run **off the main thread** (~17k points/day, re-run every fix): a `produceState` keyed on `(safeTrack, showAllTrackPoints, selectedTeamId)` computes `trackLines(sortedTrackPoints(safeTrack), filter = !showAllTrackPoints)` plus the hidden count (`raw size − kept points`, from the same input) on `Dispatchers.Default`, tagged with the team id; `valueForKey(…, selectedTeamId)` gates it, so after a team switch the previous team's lines never leak (empty until the new ones land), while within a team the last lines stay up for the few ms the next fix is filtered. `trackLinesNow` feeds the map, `trackUsable = trackLinesNow.flatten()` feeds the time span, `trackHiddenCount` feeds the map chip (always 0 with «Все точки» on — the selected chip then shows no count, by design) and TrackCard's «на карте N» (`trackShownPointCount = safeTrack.size - trackHiddenCount`, so with nothing hidden the note never flashes while a new fix is filtered). Every kept point is drawn (1-point lines as dots), so the counts match the map. `onShareTrack` re-reads the track and runs the **same** expression (so map, span and GPX always agree, and the toggle flips all three); an empty result toasts «Нет точек для экспорта». The raw `safeTrack.size` stays the «Точек» headline and the Settings «Очистить трек» count; `trackSegmentCount` (distinct `segmentId`s) is counted over raw points, so a session the filter empties still counts. Upload is untouched (always raw). `frameKey = selectedTeamId` re-frames the camera on a team switch. `mapPath = downloaded[selectedRaceId]` (a fresh path per download — MapLibre caches MBTiles SQLite handles by path for the process, see `MapFileStorage` in DATA-NOTES); `mapFileReady = mapPath != null`. `mapBase` (`MapStyleSource.Offline(path, metadata)` or `Online`) is a `produceState` reading SQLite metadata on `Dispatchers.IO`, keyed on `(mapPath, listing known)` — so a re-download over an existing map reloads the style onto the new file and **not reset to null** while reloading — a finished download swaps the base without tearing the view down (on a race switch the old base may show for one load cycle; accepted). A `LaunchedEffect(mapDownloadState)` turns `Failed` into one snackbar on **any** tab: `consumeFailure()` first, then `showSnackbar` on the composition `scope` (the state change restarts the effect and would otherwise cancel it). **Settings delete:** `mapSizeBytes` is a `produceState` on IO keyed on `(selectedRaceId, mapDownloaded, showSettings)`, computed only while `showSettings`; `mapDeleteEnabled` = file exists && `(state as? Downloading)?.raceId != selectedRaceId`; the «Удалить карту гонки?» `AlertDialog` (`showDeleteMapDialog`, reset alongside `showClearTrackDialog` on team switch and NFC launch) runs `mapRepo.delete(raceId)` on `applicationScope` + `Dispatchers.IO` — the tab updates itself via `downloaded`.

## UI layer

- `MainActivity.kt` — entry point; `HorizontalPager` swipe-tab navigation over **4 pages** (Отметки / Легенда / Карта / Команда — private `PAGE_MARKS`/`PAGE_LEGEND`/`PAGE_MAP`/`PAGE_TEAM` = 0..3 + `PAGE_COUNT` constants next to `UPLOAD_RETRY_INTERVAL_MS`, used by the pager, nav bar and every `animateScrollToPage`; see «Map tab wiring» above). **Hosts all overlay state** (see above) and the **NFC reader-mode infra** (`NfcAdapter.ReaderCallback`, enabled in `onResume`/disabled in `onPause`). A set of `@Volatile` tag hooks (`onTagScanned`, `onTagForChipInfo`, `onTagForMark`, `onTagForProvision`, `onTagForVerify`, `onTagForJudgeScan`) are armed/cleared by each overlay's `DisposableEffect`; `onTagDiscovered` dispatches them by priority on the binder thread (hence `@Volatile`) — `onTagForJudgeScan` sits in the admin-hook priority band, above `onTagForMark` but yielding to `onTagForVerify`, and hops to main via `mainHandler.post` (mirroring the other admin hooks) — and when none is armed the idle path reads `(code, uid)` once and publishes a `CapturedScan` (an unknown idle tag — not a КП, not a bound bracelet — instead plays `scanFeedback.neutral()` before dropping). `READER_FLAGS` carries `FLAG_READER_NO_PLATFORM_SOUNDS` to **suppress the stock Android NFC beep app-wide** — the `ScanFeedbackPlayer` outcomes replace it everywhere. **Deliberate silent paths** (not oversights): a provisioning tap during a pager swipe / busy job, and a recognized chip with no team selected (the picker navigation is the feedback). `nfcState: NfcState { NoHardware, Disabled, Available }` is recomputed by `refreshNfcState(enableReader)` (extracted from `onResume`) — called from `onResume` with `enableReader = true` (the lifecycle is still `STARTED` inside `onResume`, hence the explicit flag) and from the device-state receiver, which only re-arms reader mode when the lifecycle is `>= RESUMED`. **Readiness device signals:** `pollDeviceState()` — called from `onCreate` **before** `setContent` (so the first frame of the checklist never sees placeholder values) and from `onResume` (the system permission dialog pauses the activity, so resume also covers returning from it) — derives `locationAccess: LocationAccess` (FINE → `Precise`, COARSE only → `Approximate`, else `None`), `locationGranted` — a getter over `locationAccess != None`, not a second state (kept: the track, scan and `MapScreen` paths still read it), `notificationsGranted: Boolean?` (`null` on API < 33) and `powerSaveMode` (`PowerManager.isPowerSaveMode`). One `deviceStateReceiver` on `PowerManager.ACTION_POWER_SAVE_MODE_CHANGED` **and** `NfcAdapter.ACTION_ADAPTER_STATE_CHANGED` is registered in `onStart` / unregistered in `onStop` via `ContextCompat.registerReceiver(..., RECEIVER_EXPORTED)` — **exported on purpose**: `ADAPTER_STATE_CHANGED` is sent by the NFC process (uid `nfc`, not `system`), which a `NOT_EXPORTED` receiver drops (API 24–32 androidx emulation requires an app-private permission the NFC uid lacks; 33+ admits only system/same-app senders), and both actions are protected broadcasts, so no third-party app can spoof them — both toggles flip from the quick-settings shade, which does not pause the activity, so resume polling alone would miss them; permissions only change in dialogs/settings that do pause, so they stay in `pollDeviceState`. **Precise-location upgrade:** `scanPermissionLauncher`'s callback gained a COARSE-granted/FINE-denied branch — on Android 12+ a repeat FINE+COARSE request normally shows the upgrade-to-precise dialog, but once FINE is permanently denied the system answers instantly with no UI, so — only when the request was an upgrade attempt (`locationUpgradeRequest`, set by `onRequestMarkLocation` when COARSE was already granted; otherwise a user who just picked «Примерная» after an earlier full denial would get the dialog right over their choice) and FINE has no rationale — it raises a separate `showPreciseLocationDialog` («Нужна точная геопозиция» → `ACTION_APPLICATION_DETAILS_SETTINGS`, unguarded like `showLocationDeniedDialog` — it always resolves, which is why the guarded deep-links fall back to it; duplicated from `showLocationDeniedDialog`, whose text is about the track, and reset on team switch with its siblings). `onRequestMarkLocation` **always launches** (setting `locationUpgradeRequest` when `locationAccess == Approximate`) and lets the launcher callback decide. **Notifications launcher:** `notificationPermissionLauncher` (`RequestPermission(POST_NOTIFICATIONS)`, API 33+) behind `onRequestNotifications`, always launched, with the same result-side routing as location. **Permission routing** is pure `ui/common/PermissionPrompts.kt` (`locationDenialLogUpdate`/`notificationDenialLogUpdate` → `DenialLogUpdate { Set, Clear, Keep }`, `locationResultPrompt` → `None`/`DeniedDialog`/`PreciseDialog`, `notificationResultShowsSettingsDialog`, `locationSilentDenial`/`notificationSilentDenial`; `PermissionPromptsTest`) and decides **from the launcher result, never before launch**: `shouldShowRequestPermissionRationale` is `false` before the first ask, after a permanent denial, after a dismissed dialog (Android leaves the state unchanged) and after the system's unused-app auto-reset, so a pre-launch "persisted flag + no rationale" guess sent auto-reset/dismissed permissions to settings. Its `deniedBefore` input is the persisted `data/PermissionRequestLog` (`kolco24.permissions.xml`, excluded from backup; read as `container.permissionRequestLog`, not built in composition), which records a **real denial**, not a request: every callback applies the pure update — FINE (or `POST_NOTIFICATIONS`) granted → `Clear`, a denial leaving a rationale (or COARSE-only = «Примерная») → `Set`, else (dismissed / already-permanent) → `Keep` — and `pollDeviceState` also clears a flag whenever it sees the grant (e.g. made in app settings; auto-reset only revokes granted permissions, so a reset permission starts clean). Settings are routed to only when the result is a denial with no rationale **and** a real denial was recorded before this request — **or** (session fallback) an earlier *explicit* request this session already came back as a silent denial (no grant, no rationale): a permission already permanently denied with a clean flag (denied under an older build, e.g. main's session-only logic, or a denial the flag never saw) makes the system answer every request instantly with no UI, so without the fallback the checklist row / «Начать запись» tap would do nothing forever. `locationSilentDenialThisSession` (shared by the track and scan launchers; the auto-ask neither reads nor sets it) / `notificationSilentDenialThisSession` (`rememberSaveable`) feed the pure helpers' `silentDenialBefore` input; the second silent denial routes to the dialog **and** `Set`s the persisted flag (so the next session routes on the first tap). A single silent result never routes — a dismissed dialog looks identical; two dismissals in one session show the (dismissible) settings dialog, an accepted trade-off. Persisted, not `rememberSaveable`: a session flag reset on relaunch. `hasRequestedLocation` stays `rememberSaveable` only as the once-per-session guard of the first-scan auto-ask. That auto-ask is **silent on every outcome**: it sets `locationAutoAskInFlight` (`rememberSaveable`, cleared by the callback and by `onRequestMarkLocation`) and the callback passes it as `locationResultPrompt(unprompted = true)`, which always returns `None` — otherwise a permanently denied user (persisted denial flag + no rationales) got the track-worded settings dialog over the live scan overlay on the first take of every session. The NOTIFICATIONS flag is updated by this launcher's callback **and** by `trackPermissionLauncher` (it also requests `POST_NOTIFICATIONS`), so a denial from «Начать запись» counts for the checklist row; a swiped-away first prompt records nothing, so the next tap shows the dialog again; the permanent case (decided in the `notificationPermissionLauncher` callback) raises a dismissible `showNotificationsDeniedDialog` («Нужны уведомления», duplicated from `showLocationDeniedDialog`, reset on team switch with its siblings) — **never** a `startActivity` straight from the callback, since a second real «Don't allow» also returns no-rationale-after-a-recorded-denial and must not be overridden by an unexplained settings screen; its «Настройки» button opens `Settings.ACTION_APP_NOTIFICATION_SETTINGS` + `EXTRA_APP_PACKAGE` (fallback `ACTION_APPLICATION_DETAILS_SETTINGS` on `ActivityNotFoundException`; every NFC-settings deep-link goes through a local `openNfcSettings()` with `ACTION_WIRELESS_SETTINGS` → `ACTION_SETTINGS` fallbacks, since some OEM builds ship no NFC settings activity); the grant itself is re-read by `pollDeviceState` on resume. `SelectedTeamState { None, Loading, Missing(teamId), Present(team) }` drives the «Команда» tab (`Loading` suppresses the empty-state flash). `onRaceSelected` fires an on-tap prefetch of teams+legend on `applicationScope` so the network starts during the screen transition. A `LaunchedEffect` ticks `trustedClock.recomputeStatus()` every 5 s. **5-minute foreground upload retry:** next to that ticker, a `LaunchedEffect(Unit)` wraps `lifecycleOwner.repeatOnLifecycle(Lifecycle.State.STARTED) { while (true) { … ; delay(UPLOAD_RETRY_INTERVAL_MS) } }` (`UPLOAD_RETRY_INTERVAL_MS = 300_000L`) — each tick launches `trackRepo.uploadAllPending()` and `markRepo.uploadAllPending()` on `container.applicationScope` (fire-and-forget, survives backgrounding mid-batch). `repeatOnLifecycle` cancels the block when the Activity leaves `STARTED` and restarts it on return to foreground, so attempt-before-delay means a return-to-foreground is an immediate retry (deliberate); overlap with Launch B / the track service's 10-min loop / take-complete flush is safe via the repos' `Mutex.tryLock`. **60 s judge-scan upload tick:** a **separate** `LaunchedEffect(Unit)` with its own `repeatOnLifecycle(STARTED) { while (true) { … ; delay(JUDGE_SCAN_UPLOAD_INTERVAL_MS) } }` loop launches `container.judgeScanRepository.uploadAllPending()` — kept as its own coroutine rather than folded into the 5-minute loop above, since that loop's own `while(true)` never returns (a second bare `while(true)` appended in the same coroutine would be unreachable). **`uploadRefreshing` PTR host wiring:** a `remember`ed (not `rememberSaveable` — transient) `var uploadRefreshing` near `showUpload` backs `UploadScreen`'s `refreshing`/`onRefresh` params — `onRefresh` guards on `!uploadRefreshing`, runs track + marks + judge-scan `uploadAllPending()` calls (three `launch`es) in a `supervisorScope` (mirrors the Launch B precedent — one target failing doesn't cancel the others) on `applicationScope`, and clears the flag in `finally` (so a thrown repo call still stops the spinner). **Judge upload status:** a private `rememberJudgeUploadStatus(raceId, outcomes, counts)` is a race-only sibling of `rememberUploadStatus` (`produceState` keyed on `raceId`, guards `raceId != null` and `total > 0`, keys the `judgeScanUploadOutcomes` map by `raceId to target` — no team dimension, unlike the marks/track derivation) fed by `container.judgeScanUploadOutcomes.collectAsState()` and `container.judgeScanRepository::uploadCounts`; the result is passed as `UploadScreen`'s `judge` param.
- `ui/marks/MarksScreen.kt` — Отметки tab on real take data; stateless. Pure `marksToTiles(marks, costOf, colorOf)` maps **one tile per `complete=true` take** (the filter stays `complete`, not `isCounted`: an unconfirmed `cloud`/`local` take keeps its tile with `Mark.unconfirmed = isUnconfirmed()`) (an incomplete take is kept for the server log but never shown — so an unbound roster shows nothing), oldest-first so new takes append; time from `trustedTakenAt ?: takenAt`. **Tile design:** the КП discipline color fills the **whole** flat square tile (no border/stripe/elevation) so a same-discipline cluster reads as one "blob"; an edge-to-edge 4-col grid with grout showing through 2dp seams. Pure `internal tileFill(color, darkTheme)`/`gridGrout(darkTheme)` carry a **muted, screen-scoped** palette distinct from the bright `CpColor*` bars; both take a plain `darkTheme: Boolean` and the caller resolves the **applied** theme via `MaterialTheme.colorScheme.surface.luminance() < 0.5f`, **not** `isSystemInDarkTheme()` (or a manual theme override would mismatch). `null`/unknown color → the only theme-flipping neutral fill (so a colorless tile never glows). **«ВЗЯТО» counts only scoring КП** (`cost > 0`): `takenPointCount(marks, costOf)` filters distinct counted (`isCounted`) takes on `costOf(it) > 0`, denominator is the server-derived `legendScoringCount` (see `LegendRepository.scoringCountForRace`) — technical CPs (`cost = 0`, e.g. test/transfer zones) never inflate the counter. Metrics from `takenPointCount`/`totalScore`. **КВ cell (control time):** the `"metrics"` item is a private `ControlTimeMetrics` wrapper around `MetricsCard` that owns the minute tick, so only the metrics card recomposes, not the whole screen. Inputs are `MarksScreen` params (`checkpointTypes`, `controlMinutes` with defaults; `markTime`, `nowMs` **required**, so the host's trusted re-anchoring can't be silently replaced by a divergent default); MainActivity derives `checkpointTypes` (id → `CheckpointEntity.type`) from `safeCheckpoints`, `controlMinutes = tabCategory?.controlTime ?: 0`, `markTime = resolveMarkTime(m, trustedClock::trustedAt)` (same re-anchoring as the upload backfill, so the countdown matches the server and ignores wall skew) and `nowMs = trustedClock.sample().let { it.trustedMs ?: it.wallMs }` (the `localModeNow` scale), lambdas over the app-singleton `container.trustedClock` — `markTime` a plain `remember { }`, `nowMs` a `remember(clockAnchorRevision, clockStatus) { }` so every accepted trusted anchor (`TrustedClock.anchorRevision`) or status change hands down a **new seam identity** (the host decides refresh; `MarksScreen` takes no `ClockStatus`) — `clockStatus` alone is not enough: it is deduped, so an accepted re-anchor that keeps `Ok` would emit nothing and a non-ticking `Finished` would keep a duration/lateness computed against the old anchor. `now = remember(tick, marks, checkpointTypes, controlMinutes, nowMs) { nowMs() }` is re-sampled **synchronously on input change** (including a new `nowMs` identity — a new anchor re-anchors monotonic takes via `markTime`, which a static `Finished`/`NotStarted` state would otherwise never pick up) — otherwise a start take in a non-ticking state would be measured against a stale `now` and show more than the КВ until the first tick. The tick is **exact**: `LaunchedEffect(kv, tick)` (keyed on `tick` too, so a re-sample yielding an equal `kv` still re-arms) delays `msUntilNextChange(kv)` (the next whole-minute boundary counted **from the start**, not the wall minute) then bumps `tick`; `LifecycleStartEffect` (explicit `lifecycle-runtime-compose` dependency) also bumps it on `ON_START`, because `delay` runs on `uptimeMillis`, which stops while the phone sleeps. `MetricItem`'s old `isWarn` became `mono` + `isError`: the КВ cell is always `RobotoMono`, `onSurface` normally, `colorScheme.error` for `Overtime`/late `Finished`. **Known edges (not fixed):** after a reboot `trustedMs == null` until the next trusted-time anchor (server sync, GPS fix or LAN time verify), so «now» falls back to wall time while a start take may sit on the trusted scale — with a skewed clock the countdown is off until then (the `ClockWarningBanner` is visible); «now» before the start is not clamped, so «ДО КВ» may exceed the КВ. A start take with no `trustedTakenAt` from an **earlier boot** resolves to raw wall `takenAt` (`trustedAt` rejects the boot-count mismatch) while «now» is trusted — off by that boot's wall skew with no banner; with a `null` boot count `trustedAt` re-anchors the old-boot `elapsedRealtimeAt` onto the new anchor (meaningless, but identical to what the upload backfill sends). **Empty state = readiness checklist** (replaced the old single-next-step `MarksEmpty` together with `LocationNudge`/`TrackNudge`/`GhostTileRow`/`GhostTile`; the «Начать трек» nudge was dropped by product decision, `onStartTrack` survives for `TeamScreen`): while `tiles.isEmpty()` the tab renders a private `ReadinessCard` directly under `MetricsCard` (notice padding) — `MarksScreen` takes `readiness: List<ReadinessItem>?` (`null` = draw nothing) + `readinessRefreshing` (a checklist «Обновить» sync in flight → `Refresh` rows swap the chevron for a small spinner; the same flag is the double-tap guard) + `onReadinessAction: (ReadinessAction) -> Unit`; `nfcAvailable`/`nfcDisabled`/`onOpenNfcSettings` stay for the `nfc_banner`. All status/hide/text/action rules live in the pure `ReadinessChecklist` (below); the card only maps status → colour (one `readinessColor(status)` composable shared by glyphs, dot and bar: `Blocked` → `colorScheme.error`, `Warning` → `WarningAmber`/`WarningAmberDark` picked by `isDarkScheme()`, `Done` → `colorScheme.tertiary`) and forwards the tapped row's action. Anatomy: header status dot + RobotoMono «ГОТОВНОСТЬ К СТАРТУ» + `done / total`; a 3dp progress bar (a plain `Box` pair, not `LinearProgressIndicator`, to avoid M3 stop-indicator/gap artefacts at that height) — dot and bar use the `worst` status colour; rows with a status glyph (`Check` / `PriorityHigh` / `Close`), title, detail, and a chevron + `clickable` only when the row has an action; `Done` rows stay visible but muted (and keep their action where the model gives one — Team/Chips/Map link to their screen). `allDone` collapses to a single green «Всё готово к старту / Приложите телефон к метке КП» row. **`WarningAmber` is a deliberate exception** to the «one alert palette, no third amber hue» rule, which still holds for the Отметки notices (photo-review / hidden-КП cards) — the checklist needs a status distinct from `Blocked`. **First-render gate** (MainActivity): `readiness = if (readinessVisible(marksLoading, legendLoaded, mapResolved, teamMatches)) readinessItems(input) else null` — `teamMatches = readinessTeamMatches(selectedTeamId, teamStateTeamId)` (id carried by `Present`/`Missing`, `null` for `None`): `teamState` and `selectedTeamId` are independent collectors of `selectedTeam`, so a team switch could pair one team's roster with the other team's teamId-tagged bindings; - `ui/marks/ControlTime.kt` — pure (Android-free, imports only `MarkEntity`) control-time (КВ) model, port of the iOS feature. `controlTimeState(marks, checkpointTypes, controlMinutes, nowMs, timeOf)` → `Unknown` / `NotStarted(limitMs)` / `Running(remainingMs)` / `Overtime(overMs)` / `Finished(elapsedMs, late)`. - `ui/scan/ScanScreen.kt` — live stateful NFC checkpoint-marking overlay (A3). `onScanTag: suspend (ScanInput, TimeSample) -> ScanEvent`; the take persists trusted time and the 20 s window runs on the monotonic `elapsedMs` (immune to a wall-clock change). A `Mutex` serializes overlapping binder-thread taps; a `DisposableEffect` arms `onTagForMark` and on arm **drains** `pendingScan` once (the opening tap) so it is identical to later taps. A 250 ms ticker computes `remaining`; expiry finalizes then auto-closes (`currentOnClose` after releasing the mutex). `process()` plays feedback after `reduce()`: the incomplete → complete transition plays `feedbackFor(event)` for the final scan, waits `COMPLETE_FANFARE_DELAY_MS = 275L`, then plays `scanFeedback.checkpointCompleteFanfare()`; a transition guard (`!wasComplete && isComplete(...)`) means an idempotent re-tap during the hold never restarts it. **Completion** (`isComplete`) shows a `SUCCESS_HOLD_MS = 3_300L` green «Готово!» (final tick + fanfare) then closes, firing `onCompleted` (held via `rememberUpdatedState`, default `{}`) just before `currentOnClose` — expiry and manual close never call it. A FAB-opened overlay with a null session stays open until manual close. **Confirm mode (check method):** `process()` plays the ordinary tick for every tap, then asks the pure `completionOnTransition(wasComplete, session)` (`ScanSession.kt`): `None` → nothing more, `Counted` (offline take) → `COMPLETE_FANFARE_DELAY_MS` + fanfare, `Confirm(target)` → `enterConfirm(target)` (still under `scanMutex`): `confirmState = Sending(target, 1)` + bump `confirmCycle`. The target lives **in the state** (`ConfirmState.target` on both `Sending`/`Failed`) — derived once on the transition. Completion is judged on the session's **snapshotted** `expectedCount` (the live roster size taken when a `Kp` opens the take — read in `process()` through `rememberUpdatedState(roster)`, since `process` is captured once by the first-composition tag hooks), i.e. the same count the host writes into the DB row's `expectedCount`, so a roster that grows or shrinks mid-session can neither enter confirm mode for a row the DB still holds incomplete nor leave a DB-complete take unconfirmed. Completion therefore only flips on a tap; the `allScanned` effect's cloud/local → `enterConfirm` branch is defensive only (a `cloud`/`local` take never takes the offline success beat). `MarkRepository.confirm` independently refuses an incomplete row, or a target that doesn't match the row's stored `checkMethod`, with `Error` (no POST), so the loop ends «Повторить» rather than «Готово!» for a take that never counts. While `confirmState != null`: every tap is dropped **inside** the lock before `onScanTag` (so a tap queued behind the completing tap never touches the DB; no feedback), the window-expiry loop returns without finalizing/closing, the `allScanned` auto-close is skipped, `ScanTimerStrip` and the «Сканировать чипы можно в любом порядке» hint are hidden, and the top-bar «Готово» is disabled (`canFinish = checkpointId != null && (confirmState == null || completed)`). `LaunchedEffect(confirmCycle)` reads `confirmState.target` and runs the pure `runConfirm` with `attempt = { currentConfirm(target) }` (composition scope — the effect key / `finalizeSession`'s reset to 0 / leaving the overlay cancels the loop, no separate `Job` handle; an attempt in flight on `applicationScope` still finishes); `runConfirm` returning `true` → fanfare, `completed = true` (hides the status card, shows «Готово!»), `SUCCESS_HOLD_MS`, `finalizeSession()`, `onCompleted()`, `onClose()`; `false` leaves `Failed` on screen. A private `ConfirmStatus` card under the КП header shows `confirmStatusText` (spinner while `Sending`; `errorContainer` + a «Повторите отправку или закройте окно и отметьтесь на КП заново» hint + «Закрыть» / «Повторить» on `Failed` — «Повторить» acts only from `Failed` and calls `enterConfirm(failed.target)`, so the button disappears before the loop restarts and a double tap can't start two loops). **Real time bound:** the 20 s window is checked only after a failed attempt, and the cloud client uses 10 s connect + 10 s read timeouts (LAN 3 s), so on a dead cloud link `Failed` can appear up to ~40 s after completion — accepted, not shortened. `finalizeSession` resets all confirm state. System back stays MainActivity's `BackHandler` (no handler here).
