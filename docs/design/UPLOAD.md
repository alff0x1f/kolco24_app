# Выгрузка данных команды и судейских сканов (контракт)

Сверено 2026-09-30 по исходникам `~/src/kolco24/server` (`e4d4126`):
`src/apps/mobile/{urls,views,serializers,models}.py` и `src/apps/race/results.py`.
`/track/`, `/marks/`, кадры фото и `/judge_scans/` **реализованы на сервере**.
Версия, развёрнутая на cloud/LAN, и живой прогон здесь не проверялись.
Приложение хранит очередь в Room и выставляет флаги каждой цели только после
успешного ответа; ошибки оставляют данные для следующей попытки.

**Расхождения с первоначальным проектом:** сервер валидирует JSON-батчи целиком
(одна невалидная строка → `400` всего батча), трек берёт provenance из
`X-Install-Id`, а не тела. Повторные трек-точки и судейские сканы игнорируются;
отметки обновляются последней отправкой. Гарантии **fill-if-null** для
`trusted_ms` нет. `/app/time/` пока отсутствует. Подробности — ниже.

Этот документ — про **POST-выгрузку** данных команды. Чтение легенды/команд/гонок
и схема подписи — в [API.md](API.md). Подпись/заголовки/окно времени у выгрузки
**те же**, что у GET-эндпоинтов и `bindTag` (см. ниже «Общий конверт»).

| Метод | Путь | Отдаёт |
|-------|------|--------|
| POST | `/app/race/<race_id>/marks/` | батч взятий КП команды (`method="photo"` — только метаданные) |
| POST | `/app/race/<race_id>/track/` | батч GPS-точек трека команды |
| POST | `/app/race/<race_id>/mark/<mark_id>/photo/<frame_id>` | один кадр фото-отметки (сырой JPEG) |
| POST | `/app/race/<race_id>/judge_scans/` | батч судейских пиков старта/финиша (реализован; admin-bearer) |
| GET | `/app/time/?nonce=<32-hex>` | подписанное LAN-время для якоря доверенных часов (**сервер не реализован**) |

## Зачем provenance (мотивация)

На гонке возможны ситуации:

- **Два телефона за одну команду** пишут трек/отмечаются одновременно — ради
  надёжности (дублирование). Сервер должен **различать источник**, чтобы:
  - GPS-точки двух телефонов **не слились в одну ломаную** (раздельные треки);
  - повторная отметка той же КП с двух телефонов **не задвоила счёт**, но обе
    сохранились.
- **Кто-то выбрал чужую команду** по ошибке — данные надо принять, но иметь
  возможность **разобрать пост-фактум** (перенести на правильную команду).

Для отметок и судейских сканов **device-provenance** (`source_install_id`)
и снимки чипов передаются в **подписанном теле**. У трека идентификатор устройства
сейчас берётся только из заголовка; различие важно при разборе источников данных.

## Общий конверт (marks + track)

- **Те же 6 заголовков подписи** (`X-App-Key-Id`, `X-App-Sig`, `X-App-Ts`,
  `X-Install-Id`, `X-App-Platform`, `X-App-Version`), та же канонная строка
  `METHOD \n full_path \n ts \n sha256_hex(body)`, то же окно **±300 с** по
  trusted-времени, тот же `403` на плохую подпись. Тело — `application/json`, и
  его SHA-256 входит в подпись (поэтому provenance в теле — **tamper-evident**).
- **Авторизации участника нет** — это аутентификация приложения подписью, как у
  GET. Admin-bearer (как у `bindTag`) здесь **не нужен** → ветки `401` нет.
- `race_id` — в URL, `team_id` — в теле. Гонка должна быть опубликована,
  команда должна принадлежать её категории; иначе `404`.
- **Provenance:** `/marks/` и `/judge_scans/` требуют `source_install_id` в
  подписанном теле, один раз на батч. `/track/` берёт `install_id` из
  `X-Install-Id`; его JSON содержит только `team_id` и `points`. Сервер не
  сверяет `source_install_id` с заголовком. HMAC защищает поля тела, но сам
  `X-Install-Id` в канонную строку не входит.
- **Идемпотентность**: `id` — непустая клиентская строка до 64 символов
  (Android генерирует UUID, сервер формат UUID не требует). Для трека и
  судейских сканов повторный `id` подтверждается без изменения сохранённых
  данных; для отметок обновляются скалярные поля и добавляются участники.
  Батчи — до 500 элементов; пустой батч допустим.
- **Две независимые цели, один контракт**: **облако** (HTTPS, тот же хост, что
  GET-эндпоинты) и **локальный сервер события** (cleartext LAN, `192.168.1.5`).
  У обеих — та же подпись. Локальный сервер обязан валидировать те же заголовки
  тем же `key_id`/`secret` и окном ±300 с, иначе каждый
  local-upload → `403`, и `uploadedLocal` молча останется `0`. Один `id` шлётся в
  обе цели независимо — два таргета, два флага (`uploadedLocal`/`uploadedCloud`).
- **POST не авто-ретраится** на `403` (в отличие от GET/HEAD): replay ≠
  идемпотентность на уровне auth, а серверный `403` неотличим от настоящей ошибки
  подписи. Подпись и так на trusted-времени → self-heal на следующей выгрузке.

## `POST /app/race/<race_id>/marks/` — взятия КП

**Тело** (`application/json`):

```json
{
  "team_id": 1234,
  "source_install_id": "b3c4…uuid",
  "marks": [
    {
      "id": "0f9c…uuid",
      "checkpoint_id": 264,
      "method": "nfc",
      "cp_code": "9f1a…hex16bytes",
      "cp_nfc_uid": "04A2B3C4D5E680",
      "present": [
        {"nfc_uid": "04F1E2D3C4B5A6", "code": "c3d4…hex", "number": 101, "number_in_team": 1},
        {"nfc_uid": "0411223344556677", "code": null, "number": 102, "number_in_team": 2}
      ],
      "expected_count": 4,
      "complete": true,
      "trusted_ms": 1718900000123,
      "wall_ms": 1718900000000,
      "elapsed_at": 9876543,
      "boot_count": 7,
      "location": {
        "lat": 55.7501,
        "lon": 37.6109,
        "accuracy": 6.5,
        "altitude": 184.2,
        "vertical_accuracy": 3.2,
        "gps_time_ms": 1718899999000,
        "elapsed_at": 9876100
      }
    }
  ]
}
```

Поля взятия:

- `id` — клиентский UUID (тот же `MarkEntity.id`). **Ключ идемпотентности**.
- `checkpoint_id` — id КП из легенды (`checkpoints[].id`). Номер и стоимость
  сервер берёт из своей легенды (authoritative); в теле их не дублируем.
- `method` — `"nfc"` / `"photo"`. При `"photo"` тут только метаданные —
  `cp_code`/`cp_nfc_uid` пустые, `present` пустой, `complete=true`; сервер
  видит `verified=false` по пустому `cp_code` (тот же путь, что «чужая КП» в
  разделе «Краевые случаи»). **Сами байты кадров** едут отдельным бинарным
  эндпоинтом, `POST /app/race/<race_id>/mark/<mark_id>/photo/<frame_id>` —
  см. отдельный раздел ниже.
  Сервер принимает такие фото-строки вместе с NFC: пустые `cp_code` /
  `cp_nfc_uid` и пустой `present` валидны. Фото-метаданные сами по себе не
  вызывают `400`. Однако любая **невалидная** строка отклоняет весь батч:
  partial-accept из первоначального проекта не реализован.
- `cp_code` (hex, 16 байт) + `cp_nfc_uid` — **доказательство, что КП физически
  отсканирована**. `code` читается только при физическом тапе по метке, а сервер
  знает истинный `code` (сам его сгенерировал). Сырой `bid` **не шлём**: он
  публичный (есть в легенде `tags[].bid`), и по нему можно было бы форжить взятие,
  не доходя до точки. Сервер проверяет `sha256(cp_code)[:16] == bid` метки этой
  `checkpoint_id`.
- `present[]` — кто отметился, по **физической идентичности чипа**. Клиент строит
  его **слиянием** скорингового состава `MarkEntity.present` (`List<Int>`,
  источник истины по составу) со снимком участников `presentDetails`
  (`List<MarkMemberSnapshot>`, снятым на момент скана браслета — `nfc_uid` +
  `number` из привязки). Итерация идёт по `present`: где снимок есть — элемент
  обогащается, где нет (legacy-строка с `presentDetails == null`, или частичный
  снимок) — выгружается **sentinel** `{nfc_uid: null, code: null, number: 0,
  number_in_team: <num>}`. Так никто из засчитанного состава не теряется, даже на
  строках, созданных до появления снимка.
  - `nfc_uid` + `code` — снимок физической идентичности браслета. Провижининг
    уже выдаёт секретный `code` через `/member_tags/bind/`, но Android сейчас
    выгружает в `present[]` только UID и номера, `code=null`.
    При приёме сервер сохраняет эти поля без резолвинга участника по пулу;
    скоринг считает уникальные непустые UID (см. ниже).
    `nfc_uid = null` (вместе с `number = 0`) — **sentinel** «снимка нет», не
    реальный пустой UID.
  - `number` — глобальный номер участника из пула (клиентская интерпретация,
    может быть устаревшей/чужой) — для сверки. `0` — sentinel «нет снимка».
  - `number_in_team` — номер в команде, для отображения.
- `expected_count` / `complete` — что клиент считал размером ростера и засчитанным
  взятием. Сервер хранит как «мнение клиента», но при скоринге NFC
  **пересчитывает сам** число уникальных непустых UID против `team.ucount`.
- `trusted_ms` — доверенное время момента отметки (скоринг/порядок); **может быть
  `null`** (нет синка часов). **Backfill при выгрузке:** если отметка была сохранена
  офлайн (`trustedTakenAt == null`), но к моменту выгрузки якорь появился, клиент
  **вычисляет** `trusted_ms` из сохранённого `elapsed_at`+`boot_count` через
  `TrustedClock.trustedAt` в момент маппинга в DTO (строку БД не мутирует — write-once
  сохраняется), как это уже делает трек-выгрузка. **Тот же `id` может прийти
  повторно с новым `trusted_ms`.** Сейчас `/marks/` перезаписывает это поле
  последним payload, включая `null`; первоначальная гарантия fill-if-null
  **не реализована**. Повторные точки трека, напротив, не обновляются.
- `wall_ms` — сырое стенное время момента отметки. В отличие от трека (там фоллбэк
  `gps_time_ms`), у отметки GPS-времени нет, поэтому при `trusted_ms == null` это
  **единственный** фоллбэк — шлём всегда.
- `elapsed_at` — монотонный момент отметки (`elapsedRealtimeNanos/1e6`, мс);
  вместе с `boot_count` — для возможной Δelapsed-форензики. **Может быть `null`**
  (`MarkEntity.elapsedRealtimeAt` — `Long?`; NULL отличает «нет данных» от
  настоящего `0` сразу после загрузки).
- `boot_count` — boot-сессия монотонной шкалы; **может быть `null`**.
- `location` — **античит-координата места взятия**, вложенный объект; **может быть
  `null`**, когда фикса не было (`MarkEntity.locLat == null` — нет разрешения /
  GPS выключен / таймаут / отбракованный устаревший кэш). Координата пишется
  асинхронно (одноразовый свежий фикс при скане метки КП), поэтому к моменту
  выгрузки может ещё отсутствовать — это валидно. Вложенный объект (а не плоские
  поля) выбран намеренно, чтобы `gps_time_ms`/`elapsed_at` **фикса** не путались с
  одноимёнными временами самого взятия. Поля:
  - `lat` / `lon` — координата места взятия.
  - `accuracy` — горизонтальная точность фикса, метры — **ключевой
    античит-сигнал**.
  - `altitude` — высота, метры; **может быть `null`**.
  - `vertical_accuracy` — 1-сигма оценка высоты, метры
    (`Location.verticalAccuracyMeters`); **может быть `null`**.
  - `gps_time_ms` — спутниковое время фикса; **может быть `null`**.
  - `elapsed_at` — монотонный момент **фикса** (`elapsedRealtimeNanos/1e6`, мс);
    **может быть `null`**. Разница с `mark.elapsed_at` даёт **«возраст фикса»**
    (`mark.elapsed_at − location.elapsed_at`) — второй ключевой античит-сигнал
    (свежий ли фикс снят в момент взятия или подсунут старый).

**Ответ `200`**: `{ "accepted": ["0f9c…uuid", "…"] }` — список принятых
(upsert-нутых) клиентских `id`. Приложение помечает ровно их `uploadedLocal=1` /
`uploadedCloud=1` (по цели) и шлёт следующую пачку.

Повторный `id` обновляет поля `Mark` последней отправкой, сохраняя `created_at`.
`present[]` дополняется по `(mark_id, number_in_team)`: уже сохранённый слот
не изменяется. При дублях `id` внутри батча применяется последняя строка,
а `accepted` возвращает все исходные `id`. `present` ограничен 100 элементами.

Для подтверждённых NFC-отметок КП типа `start` / `finish` сервер также заполняет
нулевой `Team.start_time` / `finish_time` из самого раннего положительного
`trusted_ms ?? wall_ms` в сохранённой истории на момент первого заполнения.
Уже ненулевое время не переписывается; полнота состава для этого шага не требуется.

### Подтверждение взятия из экрана скана (`check_method` = `cloud` / `local`)

Отдельного эндпоинта нет — это тот же `POST /marks/` с батчем из **одной**
отметки. Если у метки КП `check_method` = `cloud` / `local` (снимок в
`marks.checkMethod` на момент скана), взятие засчитывается только когда
соответствующий сервер (облако / LAN) принял его, **пока открыт экран скана**.

- Когда состав полный, `ScanScreen` в режиме подтверждения на каждую попытку
  вызывает колбэк `confirm(target)` из `MainActivity`, а тот запускает
  `MarkRepository.confirm(markId, target, now)` на `applicationScope`
  (`async { }.await()`): запрос, начатый до закрытия экрана скана, всё равно
  доходит и при приёме пишет `confirmedAt`. POST одной строки
  (`backfillTrustedMs(...).toDto()`, тот же `source_install_id`) **только** в
  цель метода. Ретраи каждые 3 с, окно 20 с (`runConfirm`), затем «Повторить».
- `id` в `accepted` → `marks.confirmedAt = now` (колоночный `setConfirmedAt`,
  без бампа `updatedAt`) + флаг `uploaded*` этой цели через те же GPS-aware
  version-guard'ы, что у дренажа. `200` без `id` → ошибка; остальные ответы
  маппятся `uploadResultKind` (`Offline` / `Error`).
- Неполная строка (`!complete`) → `Error` **без POST**: такое взятие не
  засчитывается, экран скана завершится «Повторить», а не «Готово!». (Экран
  скана судит о полноте по тому же `expectedCount`, снятому при скане КП, так что
  это страховка.)
- Цель, не совпадающая с методом строки (`CheckMethod.parse(checkMethod).uploadTarget`;
  для `offline` — любая цель) → `Error` **без POST**. Снимок метода в строке
  главный: повторный скан того же КП меткой с другим методом переиспользует
  строку, и `cloud`-взятие не может быть засчитано через LAN (и наоборот).
- **В обход мьютекса дренажа** (`uploadMutex.tryLock`): идущая фоновая выгрузка
  не должна превращать подтверждение в тихий no-op. Повторный POST уже
  выгруженного `id` безопасен — сервер дедупит по UUID.
- Фоновый дренаж отметку **отправляет, но не подтверждает** — `confirmedAt` ставит
  только `confirm`. В теле `/marks/` метод и `confirmedAt` не передаются (контракт
  не менялся): сервер знает `check_method` своей метки сам. Следствие: дренаж
  отправляет и неподтверждённые `cloud`/`local` взятия тем же DTO, так что
  сервер не может отличить «подтверждено при открытом экране» от «доехало
  позже» — правило «засчитывается только подтверждённое» клиентское (открытый
  вопрос к продукту, не менялся).

## `POST /app/race/<race_id>/mark/<mark_id>/photo/<frame_id>` — кадр фото-отметки

Метаданные взятия (в т.ч. `method: "photo"`) едут обычным батчем `/marks/`
(см. выше). Сами байты кадра — отдельным, **бинарным**, не-JSON эндпоинтом,
один запрос на кадр:

- `mark_id` — `MarkEntity.id`, тот же клиентский UUID, что в `marks[].id`
  батча метаданных. Кадр может доехать только после того, как сервер увидел
  строку взятия — клиент гарантирует порядок сам (**metadata-first**): драйн
  кадров для цели стартует только когда `uploadedLocal`/`uploadedCloud` этого
  взятия для этой цели уже `1`.
- `frame_id` — стем имени файла (`<uuid>` из `marks/<mark_id>/<uuid>.jpg`, без
  `.jpg`). Стабилен и уникален на кадр — служит **ключом идемпотентности**.
  Оба идентификатора должны соответствовать `[A-Za-z0-9_-]{1,64}`.
  URL заканчивается на `frame_id`, **без завершающего слеша**.
- **Тело** — сырые байты JPEG (не JSON), `Content-Type: image/jpeg`.
  Даунскейл ≤1600px по длинной стороне, поворот уже запечён в пиксели (EXIF
  не нужен).
- **Подпись** — тот же конверт, что у всех остальных эндпоинтов (см. «Общий
  конверт» выше): те же 6 заголовков, канонная строка
  `METHOD \n full_path \n ts \n sha256_hex(body)`, то же окно ±300с.
  `sha256_hex(body)` считается от **сырых байт JPEG** — подпись не завязана
  на формат тела, только на байты. Admin-bearer не нужен (как у `/marks/`).
- Сервер проверяет принадлежность отметки гонке и хранит кадр по
  `(mark_id, frame_id)`: повтор подтверждается без перезаписи байтов.
  Фото можно приложить и к NFC-отметке — фильтра по `method` на сервере нет.
  Непустое тело ограничено 10 MiB на уровне view; JPEG не декодируется для проверки.
- **Ответ `200`/`201`** (тело клиент не парсит) — кадр принят. Клиент
  выставляет `photosUploadedLocal`/`photosUploadedCloud` только когда **все**
  кадры этого взятия приняты этой целью (флаг per-mark, per-target).

### Коды ответов (эндпоинт кадра)

| Код | Когда | Клиент |
|-----|-------|--------|
| `200`/`201` | кадр принят (upsert) | флаг взятия переключается, когда приняты все его кадры; драйн продолжает со следующим взятием |
| `404` | гонка отсутствует/не опубликована, отметка не найдена в этой гонке либо URL не соответствует маршруту | `photosUploaded*` остаётся `0`, повтор на следующей выгрузке; **останавливает всю цель** на этом триггере |
| `403` | подпись / окно времени | не авто-ретраится (POST); self-heal на след. выгрузке; **останавливает цель** |
| `429` | rate limit | бэкофф, дослать позже; **останавливает цель** |
| `5xx` / offline | сеть/сервер | дошлёт на следующем триггере; **останавливает цель** |
| `400` / `413` | пустое тело/небезопасный id (`400`), превышен лимит 10 MiB (`413`; более ранний лимит Django может дать `400`) | это взятие остаётся pending; драйн переходит к **следующему** взятию в пачке |

Транзиентные коды (`404`/`403`/`429`/`5xx`/offline) означают «эндпоинт/сеть
сейчас недоступны либо не найдены» — весь драйн для этой цели останавливается в этом
триггере. `400`/`413` означают «именно этот кадр не принят» — разовая проблема
одного взятия, соседние взятия в той же пачке не должны от неё пострадать.

**Осознанный trade-off:** «ядовитый» кадр (устойчивый `400`/`413`) или
навсегда пропавший локальный файл (килл в процессе съёмки, затем sweep)
оставляет `photosUploaded*` этого взятия в `0` навсегда — видно в
статус-строке как вечно «не загружено», а не как тихая потеря. Для
доказательных фото это осознанно лучше, чем молча посчитать доехавшим то, что
сервер не получил.

## `POST /app/race/<race_id>/track/` — GPS-трек

Команда записывает трек локально (foreground service) и выгружает **батчем** (не
стримом): на стопе, при запуске/возврате в приложение и периодически во время записи.

**Тело** (`application/json`):

```json
{
  "team_id": 1234,
  "points": [
    {
      "id": "0f9c…uuid",
      "segment_id": "7a2f…uuid",
      "lat": 55.75,
      "lon": 37.61,
      "altitude": 184.2,
      "vertical_accuracy": 3.2,
      "accuracy": 12.4,
      "gps_time_ms": 1718900000000,
      "trusted_ms": 1718900000123,
      "elapsed_at": 9876543,
      "boot_count": 7
    }
  ]
}
```

- `id` — клиентский UUID точки. **Ключ идемпотентности**.
- `segment_id` — UUID **сессии записи**: генерируется при тапе «Начать запись»,
  им помечена каждая точка этой сессии (старт→стоп). Сервер группирует по
  `(race_id, team_id, install_id, segment_id)` позволяют разделять устройства
  и сессии; `install_id` сервер берёт из `X-Install-Id`. Поле **на точке**
  (не на батче): одна выгрузка может нести точки нескольких прошлых сессий.
- `lat` / `lon` — координата.
- `altitude` — высота над эллипсоидом WGS84, метры (`Location.altitude`); **может
  быть `null`**, если у фикса нет вертикальной компоненты — сервер хранит как есть.
- `vertical_accuracy` — 1-сигма оценка высоты, метры
  (`Location.verticalAccuracyMeters`, API 26+); **может быть `null`** (нет оценки
  или Android < 26).
- `accuracy` — погрешность фикса, метры.
- `gps_time_ms` — спутниковый хинт времени (`Location.time`).
- `trusted_ms` — trusted-время **момента фикса** (из `elapsed_at` через
  `TrustedClock.trustedAt`); **может быть `null`** — сервер обязан принимать
  `null` (фоллбэк на `gps_time_ms`).
- `elapsed_at` — монотонный момент фикса (`elapsedRealtimeNanos/1e6`, мс); вместе
  с `boot_count` — для возможной Δelapsed-реконсиляции.
- `boot_count` — boot-сессия монотонной шкалы; **может быть `null`**.
- Локальный `wallMs` (back-projected wall-fallback) **не выгружается** — это
  локальный фоллбэк, сервер скорит по `trusted_ms`/`gps_time_ms`.

**Ответ `200`**: `{ "accepted": ["0f9c…uuid", "…"] }` — приложение помечает ровно
принятые `id` по цели и продолжает слать следующую пачку **до 500 точек**.

Сервер подтверждает все `id` валидного батча, включая дубли. Точки неизменяемы:
повторный `id` не обновляет координату или `trusted_ms` (даже `null → значение`).
`elapsed_at`, `gps_time_ms`, `accuracy`, `lat`, `lon`, `segment_id` обязательны;
nullable-поля — только `trusted_ms`, `boot_count`, `altitude`, `vertical_accuracy`.

## `POST /app/race/<race_id>/judge_scans/` — судейские пики старта/финиша

Эндпоинт реализован в `JudgeScanUploadView`; клиент досылает очередь на
60-секундном тике и хранит независимые флаги cloud/LAN.

Судья на точке старта/финиша сканирует браслеты участников (альтернатива
самоотметке). В отличие от `/marks/`/`/track/`, здесь **нет `team_id`** —
судейская станция сканирует все команды гонки разом, поэтому естественный
масштаб — `race_id` целиком. Источник — `JudgeScanRepository`
(`data/JudgeScanRepository.kt`), тот же дуальный (cloud + LAN) идемпотентный
батч-луп, что у трека, только без team-измерения.

**Авторизация:** в отличие от `/marks/`/`/track/`, эндпоинт требует
**admin-bearer** (`Authorization: Bearer <token>`, как у `bindTag`) — сервер
принимает пики только от админа гонки. Клиент шлёт токен той цели, куда идёт
запрос (облачный — в облако, LAN — на локальный сервер, и только при активной
аренде гонки). Нет сессии для цели → `401`, строки остаются в очереди до входа.

**Тело** (`application/json`):

```json
{
  "source_install_id": "b3c4…uuid",
  "scans": [
    {
      "id": "0f9c…uuid",
      "event_type": "start",
      "participant_number": 101,
      "nfc_uid": "04F1E2D3C4B5A6",
      "wall_ms": 1718900000000,
      "trusted_ms": 1718900000123,
      "elapsed_at": 9876543,
      "boot_count": 7
    }
  ]
}
```

- `id` — клиентский UUID (`JudgeScanEntity.id`). **Ключ идемпотентности**;
  сервер вставляет новую строку, повторный `id` подтверждает без изменения данных.
- `event_type` — `"start"` / `"finish"`. Каждая admin-подстраница
  («Отметка старта» / «Отметка финиша») жёстко зафиксирована на одном
  значении на весь сеанс.
- `participant_number` — глобальный номер участника (не `number_in_team`) —
  тем самым не нужна привязка к `team_id`. Сейчас сервер сохраняет номер;
  резолвинг участника/команды и использование этих сканов в протоколе не реализованы.
- `nfc_uid` — UID отсканированного браслета; кладётся для пост-фактум сверки,
  сервер нормализует его (`strip().upper()`) и сохраняет вместе с клиентским
  `participant_number`, без проверки соответствия номеру в пуле.
- `wall_ms` / `trusted_ms` / `elapsed_at` / `boot_count` — тот же смысл, что у
  `/marks/` (см. выше): `trusted_ms` может быть `null` (нет синка часов),
  `wall_ms` — обязательный фоллбэк; `elapsed_at`/`boot_count` — монотонная
  форензика. Клиент делает backfill времени перед отправкой (у судейских пиков
  `elapsed_at` всегда non-null; сервер допускает `null`). Но при повторном `id`
  сервер **не заполняет** ранее сохранённый `trusted_ms=null`: строка неизменяема.
  Требование fill-if-null остаётся нереализованным.
- **Каждый пик = отдельная строка**, дедуп не на клиенте — судья может
  случайно/намеренно пикнуть один браслет дважды (переотметка). Выбор зачётного
  пика — будущая серверная логика, сейчас сохраняются все разные `id`.
- **Только пулированные UID пишут строку.** Клиент отклоняет неизвестный чип и
  чип КП (ошибочный тап) до вставки — на сервер эти сканы не едут вовсе.

**Ответ `200`**: `{ "accepted": ["0f9c…uuid", "…"] }` — тот же
интерфейс `accepted`, что у `/marks/`/`/track/`, но сервер возвращает **все**
`id` валидного батча. Невалидная строка или более 500 сканов → `400` всего батча.

**Идемпотентность:** вставка с игнорированием конфликта по `id`; повторная отправка уже принятого пика
безопасна. Сканы одного участника с **разными** `id` сохраняются раздельно;
выбор зачётного пика по участнику/типу события пока не реализован.

## `GET /app/time/?nonce=<32-hex>` — подписанный LAN-источник времени

**Статус: клиент реализован, сервер — нет.** В `src/apps/mobile/urls.py`
маршрут `/app/time/` отсутствует; ниже описан требуемый, пока не реализованный
контракт. Клиент трактует неуспех как тихий no-op и не ре-якорит часы.

В локальном (LAN) режиме телефон судьи/участника может не иметь выхода в облако, а
cleartext-заголовку `Date` LAN-сервера **доверять нельзя** (MITM на event-WiFi его
подделывает). Решение — **подписанный** ответ с одноразовым клиентским nonce:
подделка `server_ms` или воспроизведение старого ответа обнаруживаются
(атакующий без `APP_SECRET` не соберёт HMAC, а реиграный ответ несёт устаревший
nonce и проваливает эхо-проверку). Источник — пустой якорь → `LanTimeVerifier`
(`data/time/LanTimeVerifier.kt`), дёргается из `SyncCoordinator.probeLocalAndRenew`
и `enterLocalMode` **безусловно** (не гейтится успехом `/sync/`-манифеста — см.
требование к серверу об исключении из окна свежести ниже).

**Запрос:** `GET /app/time/?nonce=<32-hex>` — та же подпись, что у всех эндпоинтов
(6 заголовков `X-App-*`, канонная строка включает query `?nonce=...`). `nonce` —
свежие 16 случайных байт в hex (32 символа) на каждый запрос.

**Ответ `200`** (`application/json`):

```json
{ "server_ms": 1718900000123, "nonce": "<эхо nonce из запроса>" }
```

плюс заголовок

```
X-App-Signature: hex(HMAC_SHA256(APP_SECRET, "<nonce>|<server_ms>"))
```

Требования к серверу:

- **эхо nonce** — вернуть в теле ровно тот `nonce`, что пришёл в query (клиент его
  сверяет: чужой/отсутствующий nonce → ответ отброшен);
- **`server_ms` — миллисекундная точность** эпохи (в отличие от секундного
  `Date`, поэтому LAN-кандидат точнее сетевого: `uncertaintyMs = rtt/2 + 50`);
- **подпись** `X-App-Signature = hex(HMAC_SHA256(APP_SECRET, "<nonce>|<server_ms>"))`
  тем же `APP_SECRET`, что и подпись запросов; клиент сверяет её constant-time.
- **🔴 исключить `/app/time/` из проверки свежести `X-App-Ts` (окно ±300 с).**
  Запрос несёт все 6 заголовков подписи, и сервер обязан проверять `key_id` и HMAC
  канонной строки как обычно — но **не** окно `ts`. Причина — курица-и-яйцо: клиент,
  которому нужен этот якорь, находится в состоянии `NoSync` именно потому, что его
  часы ушли; он подписывает `X-App-Ts` сырыми (уехавшими) часами и на любом
  freshness-проверяемом эндпоинте (включая `/sync/`-манифест) получит `403` — то есть
  не сможет получить то самое время, которое чинит его часы. Свежесть здесь и не нужна:
  реплей/подделку ловят **свежий per-request nonce + HMAC ответа** (`<nonce>|<server_ms>`),
  а не окно `ts`. Клиент шлёт новый случайный nonce на каждый запрос и сверяет подпись
  ответа constant-time, так что старый перехваченный ответ не пройдёт эхо-проверку nonce.

Клиент: любой не-`200` (в т.ч. `404`), битое тело, отсутствующий/неверный заголовок
подписи, RTT вне `0..10 000 мс`, несовпавший nonce → **тихий no-op** (часы не
ре-якорятся). При успехе `server_ms` пиннится к RTT-скорректированной середине
(`elapsedBefore + rtt/2`) и уходит в `TrustedClock.onTimeCandidate` — правило замены
принимает его, только если он улучшает якорь.

## Серверная модель данных (как provenance окупается)

Реализованные модели находятся в `server/src/apps/mobile/models.py`.

**Трек (`TrackPoint`)** — одна неизменяемая строка на точку, первичный ключ `id`.
Сохраняются `race_id`, `team_id`, `install_id` из заголовка и `segment_id`.
Эти поля позволяют разделять устройства и сессии при чтении; повторный `id`
игнорируется, даже если пришёл с обогащённым временем.

**Отметки (`Mark` + `MarkPresent`)** — одна строка на репорт, первичный ключ `id`. Хранит полный
provenance: `team_id` (как заявлено), `source_install_id`, `checkpoint_id`,
`cp_code`/`cp_nfc_uid`, массив `present[]` (uid/code/number/number_in_team),
времена, **античит-`location`** (координата+точность+«возраст фикса» места взятия)
и серверный `verified` (`sha256(cp_code)[:16] == bid` заявленной КП).

**Скоринг протокола** (`server/src/apps/race/results.py`, `_score_checkpoints`):

Учитываются КП этой гонки с `cost >= 0`.

- NFC: `method="nfc"`, `verified=true`, число уникальных непустых
  `present.nfc_uid >= team.ucount`. Клиентские `complete` / `expected_count`
  и соответствие UID конкретным участникам ростера не проверяются.
- Фото: КП из этого набора с `method="photo"` засчитывается без проверки участников,
  `verified`, наличия кадров или отдельного судейского одобрения.
- КП дедупятся по `checkpoint_id`; NFC имеет приоритет над фото. Неизвестные
  КП пропускаются. Два телефона создают два репорта, но один зачётный факт.
- Штраф за КВ рассчитывается по категории и `Team.start_time` / `finish_time`.
  Судейские `JudgeScan` пока не участвуют в заполнении этих времён или скоринге.

**Разбор «чужой команды» (задел):** provenance и снимки чипов сохранены,
но автоматическая сверка участника с ростером, флаги несовпадения и перенос
данных устройства на другую команду в upload-view не реализованы.

## Коды ответов, валидация батчей, краевые случаи

| Код | Когда | Клиент |
|-----|-------|--------|
| `200` | валидный батч принят, включая повторные `id` | помечает `accepted[]` как uploaded по цели |
| `400` | битый JSON, невалидная строка, нет обязательного поля, нарушены диапазоны/лимиты | останавливает выгрузку этой цели; строки остаются pending |
| `401` | у `/judge_scans/` нет действительного bearer | требуется вход в соответствующий сервер; строки остаются pending |
| `403` | подпись / окно времени; у judge — также нет права админа гонки | **не** авто-ретраить (POST); строки остаются pending |
| `404` | гонка отсутствует/не опубликована; у marks/track команда не принадлежит гонке | стоп для этой цели, строки остаются pending |
| `429` | rate limit | бэкофф, дослать позже |
| — | таймаут / IOException → `Offline` | флаг остаётся `0`, дошлёт оппортунистически |

**Фактическая валидация — весь батч целиком.** `/marks/`, `/track/` и
`/judge_scans/` сначала валидируют все строки, затем пишут данные. При одной
невалидной строке весь запрос получает `400`, ничего не сохраняется. На `200`
`accepted` содержит все отправленные `id`, включая повторы. Это подтверждено
серверными тестами `test_mark_upload_mixed_valid_invalid_batch_all_or_nothing`
и `test_track_upload_mixed_valid_invalid_batch_all_or_nothing`.

Клиент умеет обрабатывать подмножество `accepted`, но текущий сервер частичный
приём не использует. Пустой `accepted` или неуспех останавливает цикл; данные
остаются pending до следующего триггера. Постоянно невалидная строка может
блокировать свою пачку — автоматического исправления/удаления такой строки нет.

**Краевые случаи:**

- `trusted_ms` / `boot_count` = `null` допустимы у всех JSON-выгрузок;
  `elapsed_at=null` допустим у marks/judge, но не у track. `altitude` /
  `vertical_accuracy`, member `code` / `nfc_uid`, `location` и его поля nullable.
- `location == null` (нет фикса) → принимаем; отсутствие координаты — не отказ, а
  просто «нет физического доказательства присутствия» для этой строки.
- `checkpoint_id` неизвестен в гонке, но синтаксически валиден → принимаем,
  `verified=false` (данные для разбора не теряем). Только синтаксический мусор →
  `400`.
- `cp_code` не сходится с `bid` КП → принимаем, `verified=false` (не отклоняем).
- Команда другой гонки → `404`. Другая команда **той же гонки** → принимаем:
  членство отправителя и принадлежность браслетов ростеру при приёме не проверяются;
  `verified` зависит от чипа КП.
- Пустой батч → `200 { "accepted": [] }`.
- Повтор `id` → попадает в `accepted`; marks обновляется, track/judge не меняются.

Лимиты по умолчанию: `mobile-write` — 60 запросов/мин на IP для JSON-выгрузок
и провижининга, `mobile-photo` — 120 запросов/мин на IP для кадров.

**Замечание про cleartext-LAN:** на `192.168.1.5` `cp_code` / member `code` **и
`location` (координата места взятия)** идут открытым текстом. Слушающий event-WiFi
может перехватить `code` и форжить присутствие, не доходя до точки, или прочитать
координаты команд. Для облака (HTTPS) проблемы нет. Для любительской гонки риск
принят (LAN-сервер считается доверенным/изолированным); challenge-response здесь —
оверкилл.
